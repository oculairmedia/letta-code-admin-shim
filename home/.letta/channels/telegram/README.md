# Telegram channel plugin for letta-code

Second reference plugin for the admin-shim's generic channel host, alongside
`matrix/`. It exists to prove the plugin contract is not matrix-shaped: a
different transport (Telegram Bot API long-poll), the same
`createAdapter(account, host)` contract, the same account / route / status
abstractions.

Loaded from `~/.letta/channels/telegram/` per the plugin contract documented
in `admin-shim/docs/CHANNEL_PLUGINS.md`. No fork of letta-code, no build step —
the shim imports `plugin.mjs` at runtime as an ES module. **Zero runtime
dependencies**; the Bot API is spoken over node's built-in `fetch`.

## What it does

| Capability | Notes |
|---|---|
| Long-poll `getUpdates` with persisted offset | `state/<accountId>.json`; resumes cleanly across restarts |
| Bootstrap-backlog drop | fresh install (no offset file) skips updates older than process start |
| Inbound text → `onMessage` | `chatId` = `String(chat.id)`; forum topics carry `threadId` |
| Update dedupe | `state/<accountId>.dedupe.json`, 1h TTL, 5k entries, keyed by `update_id` |
| Echo filter | drops messages from the bot itself (`from.id == me.id`, cached from `getMe`) + streaming-progress markers |
| `allowedChats` enforcement | when set, ONLY listed chat ids / `@usernames` reach the agent |
| `dmPolicy` | `open` / `allowlist` — governs private chats when `allowedChats` is empty |
| Outbound `sendMessage` | plain text by default; `markdown: true` → MarkdownV2 with full reserved-character escaping |
| Threaded reply | `threadId` → `message_thread_id` (forum topics) |
| Typing indicator | `sendChatAction("typing")` with a 4s heartbeat, driven by the turn lifecycle |
| Message length | agent replies over 4096 chars are split into ordered chunks |

## Not in this rev

- Inbound media (photos/documents/voice) — text only for now; non-text
  updates advance the offset but bridge no turn.
- Inline keyboards / callback queries, reactions, edits, deletes.
- Webhook mode — long-poll only (matches the matrix plugin's model and needs
  no inbound HTTP route).

```

├── channel.json
├── plugin.mjs                 # adapter wiring: poll loop, gates, lifecycle
├── accounts.json              # NOT committed — created by the operator
├── accounts.example.json
├── README.md
├── lib/
│   ├── api.mjs                # Bot API HTTP wrapper (zero-dep, fetch)
│   ├── inbound.mjs            # update.message → inbound message
│   ├── outbound.mjs           # sendMessage (+ MarkdownV2, chunking)
│   ├── markdown.mjs           # MarkdownV2 escaping + converter
│   ├── echo.mjs               # self-echo / streaming-progress filter
│   ├── state.mjs              # offset + dedupe (file-backed)
│   └── typing.mjs             # typing indicator + heartbeat
├── state/                     # auto-managed
│   ├── <accountId>.json       # next getUpdates offset (mtime = liveness)
│   └── <accountId>.dedupe.json
└── test/smoke.mjs             # standalone exerciser
```

## Account config (`accounts.json`)

```jsonc
{
  "accounts": [{
    "channel": "telegram",
    "accountId": "lettabot",
    "displayName": "lettabot",
    "enabled": true,
    "dmPolicy": "open",           // "open" | "allowlist"
    "config": {
      "botToken":     "<bot token from @BotFather>",  // write-only secret
      "apiBaseUrl":   "https://api.telegram.org",     // override for a self-hosted Bot API server
      "allowedChats": [ -1001234567890, "@somegroup" ],
      "pollTimeoutSec": 30,
      "typingIndicators": true
    }
  }]
}
```

`botToken` matches the shim's secret-key pattern, so it is redacted in every
`GET /v1/channels/.../accounts` response (`{ __secret_set: true }`) and
scrubbed from logs — only the raw value on disk carries the token.

## Activating it (operator steps)

The committed copy under `home/.letta/channels/telegram/` is a **reference**;
it ships with no `accounts.json`, so the registry discovers it but starts
nothing. To bring up a live account:

```bash
# 1. Copy the plugin into the live channels dir (if not already there).
cp -r /opt/stacks/letta-code-parallel/home/.letta/channels/telegram ~/.letta/channels/telegram

# 2. Create accounts.json with the bot token (from @BotFather).
cat > ~/.letta/channels/telegram/accounts.json <<'JSON'
{
  "accounts": [{
    "channel": "telegram",
    "accountId": "lettabot",
    "displayName": "lettabot",
    "enabled": true,
    "dmPolicy": "open",
    "config": {
      "botToken": "123456:ABC-DEF...",
      "allowedChats": [],
      "pollTimeoutSec": 30,
      "typingIndicators": true
    }
  }]
}
JSON

# 3. Wire a chat → agent route (chat id from the inbound log or @userinfobot).
letta channels route add \
  --channel telegram \
  --account-id lettabot \
  --chat-id "-1001234567890" \
  --agent agent-local-... \
  --conversation local-conv-1

# 4. Start the adapter (or restart the shim). Via REST:
curl -X POST "$SHIM_URL/v1/channels/telegram/accounts/lettabot/start"
```

Without a route, inbound messages enter letta-code's pairing flow.

## Standalone smoke test

```bash
LETTA_HOME=~/.letta node ~/.letta/channels/telegram/test/smoke.mjs <chatId> [waitSeconds]
```

Sends a plain message and a markdown message, then tails `getUpdates` for the
wait window so you can verify inbound parsing.
